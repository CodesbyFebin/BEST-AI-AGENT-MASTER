## White-hat GitHub discoverability

- Use a clear evidence-backed About description, homepage and up to 20 genuinely relevant GitHub Topics. Remove `open-source` until a repository-wide approved license is present; `source-available` is accurate.
- Keep the README navigation concise at the top, with useful deep links to real pages, machine-readable assets and provenance documents. Links must resolve; do not invent routes to create keyword density.
- Maintain CITATION.cff with an actual maintainer, canonical repository and no fake DOI. Use GitHub releases for reproducible tagged source changes once CI and deployment qualify.
- Use meaningful issue titles and versioned changelogs. Publish original technical insights and contribution guides, not copy-pasted marketing claims or auto-generated mass pages.
- Cross-link relevant CodesbyFebin projects only where they are genuinely connected; state whether each is experimental, planned, independent or released.
- Submit the project to external directories transparently, respecting community self-promotion rules; avoid spam, sockpuppets, false rankings and paid-star exchanges.
- Record search impressions, repository traffic, GitHub stars and inbound referrals as observed metrics, never as fabricated badges. GitHub's ranking algorithms are not public guarantees.

## Ethical security outreach

Use read-only static analysis, ordinary dependency checks and consent-based testing. Source-linked MCP projects can be dangerous to run; don't install untrusted commands on the deployment runner. Do not use automated security scanning to intimidate maintainers or mislabel benign geographical network traffic as hostile.
